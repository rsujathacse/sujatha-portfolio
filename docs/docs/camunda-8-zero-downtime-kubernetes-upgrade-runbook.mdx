# Zero-downtime upgrades of a self-managed Camunda 8 cluster on Kubernetes

*A hands-on runbook: hardening, workload generation, upgrade, and rollback*

## 1. Overview

Enterprises running Camunda 8 Self-Managed need to upgrade Zeebe, Operate, and Tasklist without breaking in-flight process instances. The default Helm chart alone does not guarantee this. Upgrading across an application-version boundary can also introduce breaking changes that surface only at upgrade time.

This runbook documents a real attempt to:

- harden a cluster for zero-downtime operations; and
- execute—and recover from—a cross-version upgrade.

### Tech stack

- Camunda 8 Self-Managed Helm chart (Zeebe, Operate, and Tasklist)
- Kubernetes with a single-node k3s cluster
- Helm 3
- DigitalOcean Droplet running Ubuntu 24.04 LTS with 4 vCPU, 16 GB RAM, and a 50 GB disk
- Zeebe REST API (`v1` and `v2`) for workload generation and verification

### Upgrade path

| State | Chart version | Camunda application version |
| --- | --- | --- |
| Before | 13.13.2 | 8.8.x |
| Attempted | 14.0.1 | 8.9.x |
| Final | Rolled back to 13.13.2 | 8.8.x |

## Prerequisites

### Accounts and access

- A cloud provider account, such as DigitalOcean, with billing enabled
- An SSH key pair configured for server access

### Infrastructure

- A VM with at least 4 vCPU, 16 GB RAM, and a 50 GB disk
- Ubuntu 22.04 or 24.04 LTS

### Tools

- k3s or another lightweight Kubernetes distribution
- Helm 3
- `kubectl` (bundled with k3s)
- `curl` and Python 3

### Knowledge

- **Kubernetes basics:** pods, StatefulSets, persistent volume claims (PVCs), PodDisruptionBudgets (PDBs), node scheduling, affinity, and anti-affinity
- **Helm basics:** `values.yaml` overrides, install, upgrade, rollback, and YAML map-merge behavior
- **REST API basics:** `curl`, JSON, and HTTP status codes
- Familiarity with Camunda 8 and Zeebe concepts—BPMN, process instances, brokers, and partitions—is helpful

## 2. Environment setup

### 2.1 Droplet provisioning

The environment used a DigitalOcean General Purpose Droplet with regular CPUs: 4 vCPU, 16 GB RAM, a 50 GB disk, and Ubuntu 24.04 LTS (slug `g-4vcpu-16gb`).

Two smaller configurations were tried first and rejected:

- 2 vCPU and 4 GB RAM
- 2 vCPU, 8 GB RAM, and a 25 GB disk

Both were too constrained for a multi-broker Zeebe cluster and a multi-master Elasticsearch cluster, especially after repeated upgrade and rollback cycles.

Install k3s and Helm 3, add the Camunda Helm repository, and list chart versions to identify a genuine cross-application-version upgrade pair:


## 3. Why the default chart does not guarantee zero downtime

Inspect the chart's default `values.yaml` for the settings that determine upgrade safety:

```bash
helm pull camunda/camunda-platform --version 13.13.2 --untar
grep -E "clusterSize|partitionCount|replicationFactor" values.yaml
grep -i -A 5 "podDisruptionBudget" values.yaml
```

**Key finding:** `podDisruptionBudget.enabled` is `false` by default. A replication factor of three lets each partition tolerate one unavailable broker, but voluntary disruptions are not constrained until a PDB is enabled.

Create a canonical override file at `/root/camunda-values-override.yaml`:

```yaml
orchestration:
  clusterSize: "3"
  partitionCount: "3"
  replicationFactor: "3"
  podDisruptionBudget:
    enabled: true
    maxUnavailable: 1
```

:::note
A PDB limits voluntary disruptions that use Kubernetes' eviction API. It does not protect against every failure mode, so verify StatefulSet rollout behavior, readiness probes, broker health, and partition replication during the upgrade.
:::

## 4. Hardening the cluster

Three non-obvious problems appeared while bringing up the initial cluster.

### Issue 1: Insufficient CPU for a single-node multi-broker cluster

**Symptom:** `elasticsearch-master-1`, `elasticsearch-master-2`, `zeebe-1`, and `zeebe-2` remained `Pending` after the first installation.

**Diagnosis:** `kubectl describe pod` reported `Insufficient cpu`. `kubectl describe node` showed that the node had already reached 80 percent of requested CPU with only half of the pods scheduled.

**Root cause:** The chart's default Zeebe broker request—1000m CPU and 1500Mi memory—multiplied by three replicas, plus three Elasticsearch masters, exceeded the capacity of a single 4-vCPU node. The defaults assume a production, multi-node cluster.

**Fix:** Right-size `orchestration.resources` and `elasticsearch.master.resources` for the single-node test environment. These settings are test-only, not production recommendations.

![Kubernetes reports insufficient CPU while Camunda and Elasticsearch pods remain pending.](/img/camunda/insufficient-cpu.png)

### Issue 2: Hard pod anti-affinity blocks scheduling on one node

**Symptom:** After fixing CPU capacity, the same pods stayed `Pending`, and `elasticsearch-master-0` entered a restart loop.

Events reported that the node did not match pod anti-affinity rules. The `elasticsearch-master-0` logs showed that the pod itself was healthy but waiting to discover peers that could never schedule. It could not form quorum, so its probes failed repeatedly.

**Root cause:** The chart uses `requiredDuringSchedulingIgnoredDuringExecution`—hard anti-affinity—for Zeebe brokers. That behavior is appropriate for production, multi-node clusters, but only one broker can schedule in a single-node test cluster.

**Fix:** Overriding only the preferred, soft anti-affinity block did not replace the chart's hard rule. Helm merges YAML maps key by key, so both rules remained. Explicitly set the sibling hard-rule key to `null`:

```yaml
orchestration:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution: null
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 1
          podAffinityTerm:
            labelSelector:
              matchExpressions:
                - key: "app.kubernetes.io/component"
                  operator: In
                  values: ["zeebe-broker"]
            topologyKey: "kubernetes.io/hostname"

elasticsearch:
  master:
    podAntiAffinityPreset: soft
```

Pod anti-affinity also affected both sides of scheduling. Pods created before the fix still carried the old hard rule and continued to block new pods after the StatefulSet template was corrected. Delete those ordinal-zero pods and let the StatefulSets recreate them.

> A StatefulSet template change does not retroactively update running pods. After a scheduling-related change, verify every pod—not only the pods that were stuck.

![Camunda and Elasticsearch pods running after correcting anti-affinity settings.](/img/camunda/pods-running-after-affinity-fix.png)

### Issue 3: Elasticsearch restart cycling under memory pressure

**Symptom:** All pods reached `Running`, but Elasticsearch masters continued restarting over several hours.

**Root cause:** Memory limits tightened to fit the single-node VM—600m CPU and 1500Mi memory—were too aggressive for Elasticsearch's heap requirements. The behavior was consistent with out-of-memory termination or liveness timeouts.

**Fix:** Increase memory headroom to a 1500Mi request and a 2500Mi limit, then validate empirically until restart counts stop increasing.

![Elasticsearch pod restart counts after memory tuning.](/img/camunda/elasticsearch-restart-counts.png)

### Canonical baseline override

```yaml
orchestration:
  clusterSize: "3"
  partitionCount: "3"
  replicationFactor: "3"
  podDisruptionBudget:
    enabled: true
    maxUnavailable: 1
  resources:
    requests:
      cpu: 500m
      memory: 1000Mi
    limits:
      cpu: 1000m
      memory: 2000Mi
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution: null
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 1
          podAffinityTerm:
            labelSelector:
              matchExpressions:
                - key: "app.kubernetes.io/component"
                  operator: In
                  values: ["zeebe-broker"]
            topologyKey: "kubernetes.io/hostname"

elasticsearch:
  master:
    podAntiAffinityPreset: soft
    resources:
      requests:
        cpu: 300m
        memory: 1500Mi
      limits:
        cpu: 800m
        memory: 2500Mi
```

## 5. Generate real workload through the API

The process deployment and instance creation used direct REST API calls rather than the UI. This also produced API-level evidence for the infrastructure work.

### 5.1 API access: authentication and versioning

The first API call returned `401 Unauthorized`:

```bash
curl -s localhost:8080/v1/topology
# 401 Unauthorized: "An Authentication object was not found in the SecurityContext"
```

![The topology API returns 401 because authentication is enabled.](/img/camunda/unauthorized-api-response.png)

**Root cause:** `orchestration.security.authentication.unprotectedApi` defaults to `false`, and the test did not deploy Identity or Keycloak to provide OIDC or basic authentication.

For this isolated test cluster only, enable the unprotected API:

```yaml
orchestration:
  security:
    authentication:
      unprotectedApi: true
```

:::danger Test environments only
Never disable API authentication in production. This exception was limited to an isolated, single-node test cluster to simplify workload generation.
:::

A second issue appeared when `/v1/deployments` returned `404 Not Found`.

![The legacy v1 deployments endpoint returns 404 Not Found.](/img/camunda/v1-deployment-not-found.png)

**Root cause:** Camunda 8.8 moved the REST API to the `/v2/` base path. `/v1/topology` remains as a legacy compatibility alias, but other endpoints—including deployments—use `/v2/`.

```bash
curl -s -X POST localhost:8080/v2/deployments \
  -F "resources=@/root/simple-process.bpmn"
```

![Successful BPMN deployment through the Camunda v2 REST API.](/img/camunda/deployment-success.png)

### 5.2 Deploy the process and create instances

The test used a minimal BPMN process containing a start event, a service task, and an end event. After deploying it, create 20 process instances:

```bash
for i in $(seq 1 20); do
  curl -s -X POST localhost:8080/v2/process-instances \
    -H "Content-Type: application/json" \
    -d '{"processDefinitionId": "upgrade-demo-process"}'
done
```

![Twenty process instances created through the Camunda v2 API.](/img/camunda/process-instances-created.png)

### 5.3 Establish a measurable baseline

Use the search API to verify actual state instead of assuming the creation loop succeeded:

```bash
curl -s -X POST localhost:8080/v2/process-instances/search \
  -H "Content-Type: application/json" \
  -d '{"filter": {"processDefinitionId": "upgrade-demo-process"}}' \
  | python3 -c "import sys, json; d=json.load(sys.stdin); print('Total items:', len(d['items'])); print('States:', set(i['state'] for i in d['items']))"

# Total items: 20
# States: {'ACTIVE'}
```

Capture the pre-upgrade topology as a health snapshot:

```bash
curl -s localhost:8080/v1/topology | python3 -m json.tool
```

![Healthy pre-upgrade Camunda cluster topology.](/img/camunda/pre-upgrade-topology.png)

Confirm both PDBs at cluster level:

```bash
kubectl get pdb -n camunda
```

![Active Camunda PodDisruptionBudgets before the upgrade.](/img/camunda/pod-disruption-budgets.png)

## 6. Attempt the upgrade

The cluster now had a stable baseline: zero restarts, 20 active instances, healthy topology, and active PDBs. The next step attempted an upgrade to chart 14.0.1 and Camunda 8.9.x.

### 6.1 Review the target chart

Pull the target chart, compare relevant defaults, and review the changelog:

```bash
helm pull camunda/camunda-platform \
  --version 14.0.1 \
  --untar \
  --untardir camunda-platform-14.0.1

diff \
  <(grep -E "clusterSize|partitionCount|replicationFactor|podDisruptionBudget" -A 3 \
    ~/camunda-platform/values.yaml) \
  <(grep -E "clusterSize|partitionCount|replicationFactor|podDisruptionBudget" -A 3 \
    ~/camunda-platform-14.0.1/camunda-platform/values.yaml)
```

The diff was empty: core cluster sizing and PDB structure had not changed. The changelog included a fix related to `basic.allow-unauthenticated-api-access` and `unprotectedApi`; this was internal wiring, not a renamed override key.

### 6.2 Upgrade blocked by a new required field

```bash
helm upgrade camunda camunda/camunda-platform \
  --version 14.0.1 \
  -n camunda \
  -f /root/camunda-values-override.yaml
```

The upgrade failed before replacing any running pod:

```text
Error: UPGRADE FAILED: execution error at
(camunda-platform/templates/common/constraints.tpl:32:6):
Please configure an expected secondary storage type under
`orchestration.data.secondaryStorage.type`
```

A separate pane running `kubectl get pods -n camunda` confirmed that pod ages were unchanged.

**Root cause:** Camunda 8.9 requires an explicit secondary-storage type for the history data used by Operate and Tasklist. Camunda 8.8 inferred this value from the enabled search backend.

Add the required field:

```yaml
orchestration:
  data:
    secondaryStorage:
      type: elasticsearch
```

## 7. Recover with a rollback drill

The new chart's key structure was still unclear and the cluster became partially degraded during follow-up work. Restore the previously working Helm revision:

```bash
helm rollback camunda 6 -n camunda
```

After Elasticsearch and Zeebe re-bootstrap, verify pod state:

```bash
kubectl get pods -n camunda
```

![Camunda pods restored after rolling back to Helm revision 6.](/img/camunda/rollback-pods.png)

### Final verification

```bash
curl -s -X POST localhost:8080/v2/process-instances/search \
  -H "Content-Type: application/json" \
  -d '{"filter": {"processDefinitionId": "upgrade-demo-process"}}' \
  | python3 -c "import sys, json; d=json.load(sys.stdin); print('Total items:', len(d['items'])); print('States:', set(i['state'] for i in d['items']))"

# Total items: 20
# States: {'ACTIVE'}
```

![All 20 process instances remain active after rollback.](/img/camunda/rollback-verification.png)

**Result:** The cluster fully recovered with no observed data loss. All 20 process instances remained intact and in their pre-upgrade state.

## 8. Summary

The goal was a clean rolling upgrade across a Camunda application-version boundary, from 8.8.x to 8.9.x. The attempt instead exposed a realistic failure mode: a chart-level breaking change that surfaced at upgrade time and the safety mechanisms needed to recover.

- The Camunda 8 Helm chart needs deliberate environment-specific hardening—PDBs, scheduling rules, and resource sizing—before a zero-downtime procedure can be tested.
- Reviewing chart versions and changelogs catches some breaking changes, but not necessarily all of them. Runtime validation remains essential.
- A correctly prepared cluster, with persistent data independent of pod lifecycle and a tested rollback path, can recover from a failed upgrade without observed process-instance loss.
- The value of zero-downtime tooling is not limited to the happy path; it is the ability to survive and diagnose a failed change.
